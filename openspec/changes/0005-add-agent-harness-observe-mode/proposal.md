# Proposal

**Status:** Approved

## Why

Most SDD rules hold today only because the agent chooses to follow them: no Claude Code setting or hook enforces them. Reading `.env` is forbidden only as text in `AGENTS.md`, nothing warns when a submodule is edited without an approved change, and the AC ↔ test check (`check-impl.sh`) runs only when a skill remembers to call it, never in CI. This change adds the first layer of mechanical enforcement **in observe mode only**: it warns, it never blocks a pull request or an agent. ## What Changes

- **Deny reading secrets** in a new, committed `.claude/settings.json`: `permissions.deny` for `Read` and `Edit` of `/.env`, `/deploy/.env.prod` (both anchored at the repository root) and `**/environment.development.ts` (the files AGENTS.md section 9 names). Claude Code applies `Read` rules to its own read tools (Read, Grep, Glob); a shell command such as `cat .env` is **not** covered (see Risk). `appsettings*.json` is **not** denied: backend work legitimately reads and edits them, and only the encryption keys inside them are secret, which a path rule cannot express.
- **Ignore personal Claude Code settings**: add `.claude/settings.local.json` to the root `.gitignore`, so the committed, shared `.claude/settings.json` and the personal file (used to try a hook or a permission before proposing it) cannot be mixed up in a commit.
- **Hook 1, warn on unapproved submodule edits** (`PreToolUse`, matcher `Edit|Write|MultiEdit|NotebookEdit`): when the file is inside the `submodule` folder of a side of `openspec/sides.conf`, it finds the change from that submodule's current branch (the "Change lookup" rule of `openspec/sdd-conventions.md`) and warns when there is no matching change, more than one, or the change is not approved (`**Plan:** Approved`, or `**Status:** Approved` for a `skip_specs` change). It **always lets the edit through**.
- **Hook 2, report traceability at the end of a turn** (`Stop`): when a side's submodule has uncommitted changes and its branch maps to a change created on or after the cutoff date with `Plan: Approved`, it runs `check-impl.sh <change-id>` (work-in-progress mode, not `--final`) and shows a one-line summary if there are warnings or errors. It **never stops the agent from ending its turn** (no exit 2).
- **Both hooks fail open**: any error of their own (missing tool, path they cannot parse, timeout) ends with exit 0 and no effect on the tool call. Both read `ERAS_HOOKS`: unset or `warn` = warn, `off` = do nothing. There is no `block` mode in this change. They need only Bash, the tools the check scripts already use (awk, sed, grep) and Node (already required by the OpenSpec CLI) to parse the hook input, not `jq`. Each has a `timeout` in `settings.json`.
- **Hook self-test**: `.claude/hooks/tests/run-tests.sh` feeds sample hook inputs (a parent-repo path, a submodule path with an approved change, without a change, with an unapproved change, a Windows path with backslashes, broken JSON, `ERAS_HOOKS=off`) and checks the exit code and the output.
- **CI, traceability in the ship PR (non-blocking)**: `.github/workflows/sdd-checks.yml` gets one more step. When the PR changes the pointer of at least one side's submodule, it runs `check-impl.sh <id> --final` for each active change the PR touches that has `Plan: Approved`, is not `skip_specs` and was created (`created:` in `.openspec.yaml`) on or after the cutoff date `HARNESS_SINCE`. The job keeps its existing `continue-on-error: true`.
- **Cutoff date (grandfathering)**: `HARNESS_SINCE` is the date this change is approved, written in the workflow and in the hook. Changes created before it (today `0000`, `0001`, `0003`, `0004`, `571`, `578`, `642`, `660`, `672`) are skipped by Hook 2 and the CI step, with a one-line notice. Hook 1 applies to every change, because it only warns.
- **Docs**: one paragraph in `CLAUDE.md` ("Claude Code specifics") saying what the deny rules and the two hooks do, that they only warn, and how to switch them off (`ERAS_HOOKS=off`); one row in the "Checks" line of `openspec/sdd-conventions.md` for the hook self-test.

**Out of scope (see Follow-ups in `tasks.md`):** any blocking mode (hook exit 2, removing `continue-on-error`, required status checks); the backend format and `-warnaserror` gates in `ERAS-BE` CI (they depend on `578-fix-dotnet-format-baseline`); architecture tests; drift or stale-change routines; denying shell reads of secrets; gating edits to infrastructure files (`.github/`, `deploy/`, `nginx/`, `docker-compose*.yml`); and any edit under `ERAS-BE/`, `ERAS-FE/` or `ERAS-FE-React/`.

## Impact

- **Sides / submodules:** none (parent repo only). No side of `openspec/sides.conf` changes; the hooks only read it.
- **Files:** `.gitignore` (one line), `.gitattributes` (one line), `.claude/settings.json` (new), `.claude/hooks/hook-lib.sh` (new), `.claude/hooks/require-approved-change.sh` (new), `.claude/hooks/report-traceability.sh` (new), `.claude/hooks/tests/run-tests.sh` (new), `.github/workflows/sdd-checks.yml` (one step added), `CLAUDE.md` and `openspec/sdd-conventions.md` (one paragraph and one row).
- **Roles / who can do what:** no change for ERAS users. For contributors who use Claude Code in this repository: the agent can no longer read the three secret files with its read tools, and it sees warnings. Nothing else changes for people who do not use Claude Code.
- **API contract:** none
- **Data / migration:** none
- **Risk (low, contained by the observe mode):**
  - *A pull request blocked by a new rule:* not possible in this change. The CI step runs inside a job that is already `continue-on-error: true`, and only for changes created after the cutoff.
  - *An agent blocked by a hook:* not possible by design (no exit 2, fail open, a timeout). The worst case is a wrong or noisy warning, which `ERAS_HOOKS=off` silences.
  - *Hooks on Windows:* the team works on Windows with Git Bash. Task 1.2 confirms how Claude Code runs a hook command on Windows before any hook is written. If it cannot run reliably, the hooks are dropped from this change and only the deny rules and the CI step ship.
  - *Ship PR timing:* `check-impl.sh` reads only active changes (`openspec/changes/<id>`), so once the archive commit is pushed the change is skipped. The step therefore checks the ship PR on the commits before the archive; the archive itself is still gated by `check-archive.sh`. Teaching `check-impl.sh` to read an archived change is a follow-up.
  - *Deny rules are not a boundary:* they stop the agent's read tools, not `cat .env` in the shell. They reduce accidents; the rule in AGENTS.md section 9 still applies.
  - *Baseline:* measured in task 1.3 against the active and archived changes before anything is enabled; any check that fails on a legitimate case is a bug in the check, fixed before it ships.
  - *Baseline result (task 1.3, 2026-11-18):* `ERAS-BE` and `ERAS-FE` are on a detached HEAD and `ERAS-FE-React` on `develop`, so today Hook 1 would warn on any submodule edit ("no branch maps to a change"), which is the intended rule; the warning names the detached HEAD so the fix (create the change branch) is obvious. `660` has no `**Status:**` line, so a branch mapped to it would warn as not approved. `check-impl.sh --final` gives `642`: 1 error (1 task unchecked, true) and `672`: 19 errors with 0 open tasks, because the checked-out `ERAS-FE` commit does not hold its tests: the result depends on which submodule commit is checked out, which is why Hook 2 never uses `--final` and why every change created before `HARNESS_SINCE` is skipped. On the ship PR the submodules sit on the bumped commits, so the CI step sees the real tests. Both are skipped (created before the cutoff); `0004` and `0005` fall on the cutoff date but are `skip_specs`, so they are skipped too.
  - *Turn delay:* `check-impl.sh` takes about 10 s on Windows Git Bash (measured on `642` and `672`). Hook 2 runs it only when a submodule has uncommitted changes on a branch of an approved post-cutoff change, so the delay hits implementation turns only; its timeout is 60 s.
- **Rollback:** every group in `tasks.md` is one commit and can be reverted on its own. Deleting `.claude/settings.json` removes the deny rules and both hooks at once; `ERAS_HOOKS=off` disables the hooks without a commit.

No behavior of ERAS changes, so this change sets `skip_specs: true` (AGENTS.md section 3, tooling and CI).

## Decisions

**Task 1.1, Claude Code docs read on 2026-11-18** (code.claude.com/docs/en/hooks, /settings, /permissions; the pages show no version or date, only feature versions such as v2.1.295):

- *Hook registration:* `hooks.<Event>[].matcher` + `hooks[]` with `type: "command"`, `command`, `timeout` (**seconds**, default 600 for a command hook). `Stop` takes no matcher. A matcher made only of names and `|` matches tool names exactly (`Edit|Write|MultiEdit|NotebookEdit`). The hook command is `bash "${CLAUDE_PROJECT_DIR}/.claude/hooks/<name>.sh"`; `CLAUDE_PROJECT_DIR` is exported to the hook.
- *Input:* PreToolUse gets `tool_name` and `tool_input`; `tool_input.file_path` is absolute with the platform's separators (backslashes on Windows); NotebookEdit uses `tool_input.notebook_path`. Stop gets `stop_hook_active`, `cwd` and `last_assistant_message`.
- *Exit codes:* 0 = success, its stdout JSON is applied; 2 = blocks (PreToolUse) or forces the agent to continue (Stop), **never used here**; any other code = a non-blocking "hook error" notice and the call proceeds.
- *Non-blocking warning:* top-level `systemMessage` ("warning message shown to the user") plus `hookSpecificOutput.additionalContext` with `hookEventName` `PreToolUse` or `Stop` for the agent. Plain stdout or stderr with exit 0 never reaches the agent on these events. Whether `systemMessage` is shown on PreToolUse and Stop is checked in task 1.2.
- *Windows:* a shell-form hook runs through Git Bash, or PowerShell when Git Bash is not installed; without Git Bash `bash …` fails with a non-zero, non-2 code, which is a non-blocking notice, so the hooks still fail open.
- *Deny rules:* `Read(./.env)` style, paths relative to the current directory, gitignore globs (`**/environment.development.ts`). A `Read` deny also covers Grep and Glob (best effort), the Edit and Write tools, and Bash commands that name the file (`cat`, `head`, `tail`, `sed`, `tee`, redirections); it does **not** cover commands that read files without naming them (`grep -r`, a script opening the file). NotebookEdit needs an `Edit` deny. So the Risk line "a shell command such as `cat .env` is not covered" is narrower in practice: only shell reads that do not name the file escape the rule.

**Task 1.2, hook probe on Windows (2026-11-18, throwaway hook in `.claude/settings.local.json`):** the hook ran in Git Bash 5.3 with `node` on the `PATH`; a hook added to the settings file was picked up without restarting the session. `CLAUDE_PROJECT_DIR` arrives as `c:/workspace/ERAS` (forward slashes, lower-case drive) while `cwd` and `tool_input.file_path` arrive as `c:\workspace\ERAS` and `C:\…` (backslashes, either case), so the hooks normalize separators and compare paths case-insensitively. `hookSpecificOutput.additionalContext` on PreToolUse reached the agent next to the tool result. `.claude/settings.local.json` is **not** git-ignored in this repository, so it is deleted after the probe. The user saw both `systemMessage` warnings in the chat ("PreToolUse:Write says: …" and "Stop says: …"), so `systemMessage` is shown to the user on both events. The Stop input held `stop_hook_active` (false), `cwd`, `last_assistant_message`, `background_tasks` and `session_crons`.

**Scope amended on 2026-11-18**, at the request of the change author (stated in chat) after task 1.2 found that `.claude/settings.local.json` is not git-ignored: the root `.gitignore` now ignores it (task 2.2), so the personal file this change recommends for trials cannot be committed by mistake.

**Tasks 2.1 and 2.2 (2026-11-18):** the rules use the `/path` form (relative to the project settings, that is the repository root) instead of `./path` (relative to the current directory, which changes when a command runs inside a submodule): `Read(/.env)`, `Read(/deploy/.env.prod)`, `Read(**/environment.development.ts)` and the same three with `Edit`. They were verified **without reading any real secret**: with two temporary rules of the same forms on decoy files, the Read tool, Grep and `cat` in Bash were all refused for a root-anchored decoy and a nested `environment.development.ts` decoy, while a nested `allowed.txt`, `.env.sample` and a decoy `appsettings.json` were read normally (the real `ERAS-BE` `appsettings.json` was not opened, since it may hold encryption keys). The temporary rules and decoys were removed. `git check-ignore -v` names `.gitignore:3` for `.claude/settings.local.json` and nothing for `.claude/settings.json`.

**Group 3, hooks (2026-11-18):** a small shared library, `.claude/hooks/hook-lib.sh`, holds the change lookup, the approval and cutoff reads, path normalization, the once-per-session marker and the JSON output, so the two hooks do not duplicate them (one file more than the first Impact list). Hook 1 warns through `systemMessage` and `additionalContext`, each distinct warning **once per session**. Hook 2 uses `systemMessage` **only**: the docs say `additionalContext` on Stop makes the conversation continue, which an observe-mode warning must never do; it shows a result once per session and only when it changes. Self-test: 23 cases, all green; a mutation (cutoff moved to 1999, `off` switch broken) made exactly the 3 related cases fail, so the cases can fail. Real session on Windows (task 3.4): a probe file written in `ERAS-BE` (detached HEAD) got the warning and was written; it was deleted right after. Hook 2 on the real repository ran in 0.36 s and stayed silent, as expected: no submodule branch maps to an approved change created on or after the cutoff, so its warning path is proven by the self-test only (where `check-impl.sh` takes about 10 s). Task 3.5: an `env` block in `.claude/settings.local.json` is **not** applied to a session already running (the probe in `ERAS-FE` still warned), so `ERAS_HOOKS=off` is proven by the self-test and needs a check in a new session (set `ERAS_HOOKS=off` in the shell before starting Claude Code, or in `.claude/settings.local.json` `env`, then restart). **Done on 2026-11-18:** with `{"env":{"ERAS_HOOKS":"off"}}` in the git-ignored `.claude/settings.local.json`, a new Claude Code session wrote and deleted `ERAS-BE/zz-probe.txt` (detached HEAD) and no warning reached the user or the agent, while the same write in a session with the hooks on had warned.

**Group 4, CI step (2026-11-18):** the step has `if: ${{ !cancelled() }}`, a setting not named in "What Changes": without it GitHub skips the step whenever an earlier step fails (for example `check-plan.sh` on an older change), even though the job is `continue-on-error`, so its result would often be invisible. It reads the sides from `openspec/sides.conf` through `sides.sh`, like the scripts. Local run of the step's script: on this branch against `develop`, no pointer moved and the step skips; in a fixture repository, a spec-only PR skips, a PR that moves `ERAS-BE` skips a pre-cutoff, a `skip_specs` and a `Plan: Draft` change with one notice each and runs `check-impl.sh --final` on the post-cutoff approved change (exit 1 with no tagged test, exit 0 once the test exists). The workflow parses as YAML (`yaml` 2.5.1, strict) with `continue-on-error: true` kept and only the new step added.

**Line endings (found in task 6.3):** `.gitattributes` forced LF only for `.claude/skills/**/*.sh`. A clone with `core.autocrlf=true` would check the hook scripts out with CRLF, and Git Bash would then fail on every hook call (non-blocking, but a "hook error" notice on each edit). One line, `.claude/hooks/**/*.sh text eol=lf`, was added to `.gitattributes`, the same rule the skills already use; `git check-attr eol` now gives `lf` for the hook scripts.

**Task 6.2 (2026-11-18):** the change was pushed to the existing PR #694 (branch `refactor/0000/improve-sdd`, head `b4fe6c5`, not a draft; the workflow runs on every `pull_request` push, draft or not), as the reviewer asked for one branch. Run 44413340940 of `sdd-checks.yml` passed. Every step succeeded, and the new step printed "This pull request moves no submodule pointer (not a ship PR): nothing to check.". `check-plan.sh`, `check-adr.sh` and `check-spec.sh` gave 0 errors for 0000, 0001, 0003, 0004 and 0005. The only warnings were the known ones: no `**Plan:**` line in the `skip_specs` changes, and missing sign-offs on older ADRs.

**Task 1.4, baseline:** `run-tests.sh` 141 passed, 0 failed; `check-skills.sh` 8 skills, 0 errors.
